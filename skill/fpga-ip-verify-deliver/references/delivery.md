# 从文件整理到接收者可运行

## 1 明确发布范围

board_retest：离线开发/构建准入已满足，供接收者按步骤实板验证；实际板端未测写明。accepted：当前硬件/软件版本从干净启动实测通过，记录方法、环境和证据。两者都要求完整文件，不能以复测版为理由漏掉软件或依赖。

完整交付至少包含 hardware、software、models（如有）、environment、engineering、validation、samples、部署 README 和 rollback。目录名可变，manifest 用角色描述内容。可另附轻量部署包，但不能用它取代用户要求的完整工程包。

## 2 硬件与构建来源

PYNQ+XRT 四件套为 bit/hwh/xclbin/xsa。它们来自同一最终硬件设计/最终链接：普通 Vivado 导出不等于 Vitis 可链接平台；最终链接后的 DPU/端口必须在最终 HWH/XSA 中核实。不要把前期静态 XSA、旧 HWH 与新链接 bit 混装。PYNQ 普通路线用 pynq profile，不人为制造 xclbin。

从正式构建目录复制实际输出，保存源码版本/树哈希、工具/IP/运行库版本、器件、许可证状态、精确命令、日志、DRC/时序/资源。build_record 按 artifact 角色记录路径/SHA，并与 manifest 对应。相同 build_id 字符串只能支持追溯，不能单独证明同次生成，须审查实际日志和产物来源。

带真实 XPR、BD、自研 RTL、全部 IP 源码/元数据、XDC、初始化文件、TB、构建/重新封装脚本。要求可编辑 IP 时包含对应源码/编辑工程。有许可证或不能分发的依赖，用明确版本、官方获取方法和许可要求说明，不私自塞入许可文件。接收者缺许可时不能承诺可重建。

## 3 软件与系统依赖

明确解释器、OS/PYNQ/XRT/VART/库版本、目标 ABI、依赖文件/安装命令、入口配置。提交源代码以及需要的本地编译库与构建方式，不依赖作者个人目录。DMA/帧传输、DPU Runner、CPU 末层/后处理、显示初始化、模型/标签/预处理等按实际功能齐全。

摄像头打开不等于送入 PL，必须包含 frame_transport；HDMI HWH 实例存在不等于出图，必须包含 TX/PHY/时钟器件初始化与显示程序。模型含 CPU 头时交付对应权重/规格，不只交 xmodel。设备树/驱动有要求时提供源、部署/校验/回退和重启条件。

start/stop/diagnose 不应是空占位，写出参数、执行位置、权限、环境及设备就绪检查。SD 文件复制不会自动运行；JTAG bit 不替代 Linux/PS 初始化。自启动只有在明确部署范围内才配置和验收。

## 4 从清单到 ZIP

1. 冻结交付 ID，整理到新的 staging 目录，先保留原版。
2. 填 manifest：profile/stage、所有特性布尔值、逐文件 role/path/SHA、硬件 build_id、验证状态和证据路径。多份同角色工程源码可重复 role，最终 bit/hwh/xsa/xclbin 各一份。
3. 生成 build_record 对应条目。人工检查时序/DRC/仿真结果，不是填 PASS 后就算完成。
4. 执行 audit，修复 BLOCKED/FAIL。审查 unlisted_not_packaged：如是运行依赖，先纳入；如是缓存不纳入，说明选择。脚本只打包已审计文件。
5. 执行 pack，保存输出 ZIP SHA。其 CRC 和成员 SHA 通过只证明传输与文件身份。
6. 解压到全新目录，重跑 audit，打开实际 XPR，检查外部引用；执行真实构建或可重复构建验证，不能只运行“生成工程 Tcl”。干净目录运行软件并核对相对路径。

清单中不能把一个文件标为多个 role；不同角色如同一文件有多个用途，可创建明确的不同配置/文档文件或扩展 schema 后测试，不靠改空后缀凑齐。模型特性等应按实际工程填 true，不能为躲过检查填 false。

## 5 接收者验收

先校验包，再核对板卡镜像/设备树/内存策略，加载本次硬件、确认时钟/身份、初始化、已知输入→输出对照、持续运行、正常停止、重启重现。显示业务需要现场画面。记录 boot_id、版本哈希、命令日志、错误和稳定运行时长。无远程板卡时交给接收者执行，不伪造证据。

accepted 发布前必须实际完成干净启动与目标业务，不以“进程启动”“Runner创建”“一次结果返回”代替。验收范围和未通过项写入 README，下一位拿到包知道能做什么、还差什么以及如何回退。
