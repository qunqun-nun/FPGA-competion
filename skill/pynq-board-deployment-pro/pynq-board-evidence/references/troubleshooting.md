# 故障诊断与修复

## 1. 无法识别PYNQ设备

**现象**：`No devices found, is the XRT environment sourced?`或`RuntimeError: No Devices Found`。

**定位**：交互终端可以运行，而sudo或systemd进程缺少XRT环境；解释器可能不属于PYNQ环境。

**处理**：在导入PYNQ前显式配置环境。

```sh
sudo env XILINX_XRT=/usr \
  /usr/local/share/pynq-venv/bin/python3 /实际工程/运行入口.py
```

**结果**：设备枚举恢复。该结果仅说明设备可识别，后续仍需验证Overlay下载、指纹和推理。

## 2. Overlay加载停在xclLoadXclBin

**现象**：xclOpen和xclLockDevice正常，xclLoadXclBin不返回。

**定位**：最终HWH、XSA、XCI与功能网表显示，公共控制复位的低有效aux_reset_in被固定为0。局部仿真确认interconnect_aresetn持续为0，改为1后释放。

**处理**：将未使用的低有效辅助复位输入明确固定为1，重新生成同次bit/hwh/xclbin；公共控制及DPU相关时钟域同步核对。

**结果**：V0.16实板下载返回0，Runner创建和单图推理完成。这属于硬件连接修复，无法仅通过修改Python解决。

## 3. CU中断初始化失败

**现象**：`Failed to initial CU interrupt. Fall back to polling`。

**定位**：ZOCL设备树缺少对应IRQ资源，与xclbin中的CU中断配置未完成对接。

**处理**：依据实际PL→PS连线、CU中断编号及设备树配置实现匹配中断方案；在支持轮询的既有路径中保留轮询并验证运行。

**结果**：V0.16仍出现中断告警，但轮询完成单图推理。因此不能将该告警单独认定为加载卡死根因，也不能声称中断已修复。

## 4. 模型指纹查询错误或辅助工具缺失

**现象**：`DPU subgraph has no fingerprint`，或未安装xdputil。

**处理**：实际模型属性为`dpu_fingerprint`，应按图元数据读取并严格比较；Overlay加载成功后，可按硬件元数据只读指纹寄存器。辅助工具缺失不等于驱动缺失。

**结果**：模型目标指纹与V0.16实际硬件读回一致。文件推导值和硬件读回必须分别记录。

## 5. CPU Runner库无法加载

**现象**：`libvart-cpu-runner.so: cannot open shared object file`。

**定位**：模型包含1个DPU子图和6个CPU末层分支，六路输出尚未形成最终框；参数常量已包含在XModel中。

**处理**：提取同一模型的权重、偏置及fix属性，实现专用六路1×1卷积，再执行DFL、sigmoid、NMS和坐标还原。严格按张量名匹配，保持DPU_ROUND舍入语义。

**结果**：六路、五种完整形状合成输入共273万个卷积输出与独立C++参考逐值一致；后续真实DPU联合执行通过。该路径未安装通用CPU Runner插件，旧GraphRunner程序不会自动恢复。

## 6. 启动设备树缺少内存保留

**现象**：`Boot DT lacks no-map reservation 0x20000000+0x4b0000`。

**定位**：工程使用固定物理DDR区域，但默认启动设备树没有排除Linux分配。root权限不能替代内存保留。

**处理**：停止硬件访问，使用已验证镜像启动后重新执行内存检查。本板临时启动命令为：

```text
fatload mmc 0:1 0x10000000 image17.ub
bootm 0x10000000
```

**结果**：root检查通过后允许加载。持久选择镜像前，应确认实际启动脚本支持的机制并备份。上述分区和地址仅适用于本案例。

## 7. FCLK0在运行时恢复为150MHz

**定位**：单次设置正确，但Overlay下载或Runner创建可能再次配置时钟。

**处理**：增加运行时分频适配，并在加载后、Runner后及持续运行阶段检查频率。

**结果**：寄存器推算约99.999MHz。该结果不是示波器测频。FCLK0、HDMI像素时钟和PHY参考时钟不可混为同一参数。

## 8. HDMI器件地址及配置回读失败

**定位**：输出DP159位于0x5e；0x5c为输入TMDS181。IDT在已配置状态下的身份寄存器可能不同于工厂状态，DP159部分位为动态位或自清位。

**处理**：只向正确输出器件配置；IDT执行两次完整稳定读取并验证工厂态或已知配置态；按审阅过的掩码比较稳定位。设置视频时钟后再次初始化，验证重复接管。

**结果**：V0.17.3器件探测、重复初始化和完整显示链验证通过。不得修改读回值或忽略未知配置以强制通过。

## 9. IDT短传输导致摄像头启动失败

**现象**：`Short IIC send address=0x6c expected=2 actual=1`。

**定位**：错误出现在时钟配置回读阶段，而非摄像头解码或DPU执行；电气根因未确定。

**处理**：保留39字节逐字节校验，将相邻寄存器合并成7个连续读块。仅在明确短传输且两次状态快照满足总线空闲、FIFO空和无仲裁丢失等安全条件时，完整重发指针并重读，最多3次，间隔2/4ms。写配置不自动重试，状态不明时停止。

**结果**：15项本机和15项板端测试通过，随后5次完整会话成功。真实会话未触发重试，因此恢复分支的证据来自故障注入，不能声称已完成实板NACK现场恢复。

## 10. 有图、失锁与黑屏

**现象**：初始化返回但屏幕无图，或运行中报`Video bridge lost lock`。

**处理**：分别核查显示器电源/输入、输出口、EDID、HPD、PLL、参考频率和桥接锁定；确认程序仍在运行。屏幕未开或测试已结束门控输出时，应重新建立有效观察窗口。

```sh
sudo systemctl restart fengyan-camera.service
journalctl -b -u fengyan-camera.service --no-pager -n 30
```

**结果**：重新启动后日志和现场图像确认出流。显示器电源与失锁在时间上相关，但不足以单独确定失锁根因。HDMI_INIT_OK、STREAM_UP和可见画面分别验收。

## 11. 检测结果为空或没有文字

空预测应固定同图、同预处理比较浮点/量化参考，并保留真实DPU特征。降低置信度只能用于诊断，不能代替精度修复。指定五张图片在默认阈值下正常出框，说明早期其他样本的空结果不能推广到全部输入。

OSD仅实现矩形框时，无文字属于功能范围限制，不应按字体故障处理。

## 12. 帧身份不一致与摄像头积压

Fresh-Frame请求可能引用前一完整帧。PS应按frame_id查找对应提交图像，并校验buffer_id及generation，禁止将DDR内容与最新摄像头帧直接比较。

V0.17调度器在没有FREE槽时回收旧且未占用的READY槽，保留最新完整帧，不覆盖WRITING或DPU_OWNED。摄像头线程持续读取并只保留最新帧；其主动跳帧与PL dropped应分开统计。

## 13. 自启动与手动运行不一致

**定位**：服务环境缺少XRT，或默认Overlay加载、PL状态清理、Jupyter间接依赖与应用竞争。

**处理**：显式配置环境并检查服务依赖。记录原状态后调整相关服务，增加摄像头就绪等待、内存检查和失败退出。

**结果**：修复版正常重启及独立供电冷启动完成出图验证。模型切换后的新版本仅完成对应运行验证，未重复执行的冷启动不得沿用为该版本结论。

## 14. 串口占用及传输截断

Access denied时检查其他终端是否独占端口；无返回时核查供电、线缆、枚举和登录状态。长命令出现续行提示时取消未完成输入，核对已传长度及前缀哈希，再分段续传并验证整体哈希。禁止在未知状态下重复追加。

## 15. 工具链与平台迁移

独立综合曾出现`TclStackFree: incorrect freePtr`，单线程未解决；保留仿真与BD证据，并在匹配工具版本完成正式集成。平台迁移时，IP仓库相对路径失效可导致generate_target失败；应使用经过验证的可链接平台、完整IP源及对应构建脚本，不以摘要有效替代平台可重建性。
